ROUND 3: SYSTEM DESIGN (LOW-LEVEL DESIGN)
LLD 3.1: Design a Single Data Pipeline with Retry and Recovery
Category: Component Design + Error Handling

Real-World Context (Hevo Platform):
A Hevo pipeline reads from a PostgreSQL source, transforms data (flattening JSON, type casting), and writes to Snowflake. Network blips, destination throttling, and transient errors are common in production. The pipeline must retry failures with exponential backoff, checkpoint progress to resume after crashes, and handle partial batch failures (e.g., 990 records succeed, 10 fail due to schema mismatch). This design is the core building block of Hevo's 150+ source-destination connectors.

Problem Statement:
Design a data pipeline processor that reads from a source, applies transformations, and writes to a destination. The pipeline must handle failures gracefully with retry logic, maintain checkpoints for recovery, and support exactly-once processing semantics.

Requirements:

Components to Design:

SourceReader: Reads data from source (database, file, queue)

TransformationEngine: Applies data transformations

DestinationWriter: Writes processed data to destination

CheckpointManager: Manages offset/position tracking

RetryHandler: Handles failures with exponential backoff

Challenges:

Source read failures (connection issues, timeouts)

Transformation errors (invalid data, business logic failures)

Destination write failures (downstream service unavailable)

Partial batch failures (some records succeed, some fail)

Recovery after process crash (resume from last checkpoint)

Example Scenario:



Pipeline Processing:
Source: Database table (read 1000 records at a time)
Transform: Parse JSON, validate fields, enrich data
Destination: REST API
Normal flow:
→ Read batch (offset 1000-2000)
→ Transform 1000 records
→ Write to API
→ Checkpoint offset 2000
→ Continue from offset 2000
Failure scenario:
→ Read batch (offset 2000-3000)
→ Transform 1000 records
→ Write to API fails (503 Service Unavailable)
→ Retry with exponential backoff (1s, 2s, 4s, 8s)
→ After 5 retries, still failing
→ Store failed batch in error queue
→ Checkpoint offset 3000 (skip failed batch for now)
→ Continue processing
Recovery scenario:
→ Process crashes at offset 5000
→ On restart, read checkpoint (offset 5000)
→ Resume from offset 5000 (no duplicate processing)
What to Look For:

Design Patterns:

Reader-Transformer-Writer pattern

Retry with exponential backoff

Checkpoint pattern for state persistence

Circuit breaker for downstream failures

Error queue for failed records

Key Decisions:

Batch size (performance vs memory tradeoff)

Checkpoint frequency (after every batch vs every N batches)

Retry strategy (exponential backoff parameters, max retries)

Error handling (fail fast vs skip and continue vs DLQ)

At-least-once vs exactly-once semantics

State Management:

Where to store checkpoints (file, database, Redis)

Checkpoint format (offset, timestamp, record ID)

State recovery on restart

Idempotency handling (avoid duplicate writes)

Performance Optimization:

Parallel processing (multiple threads/workers)

Batching for throughput

Connection pooling

Async I/O where possible

Monitoring:

Records processed per second

Error rate and error types

Retry attempts and success rate

Lag (current offset vs source's latest offset)

Checkpoint age (time since last checkpoint)

>>>>> LLD 3.2: Design a Batch Job Processing System <<<<<<
Category: Job Scheduling + Parallel Execution

Real-World Context (Hevo Platform):
Hevo runs scheduled batch jobs for full table syncs (daily snapshot of entire database), aggregation pipelines (compute daily rollups), and maintenance tasks (schema refresh, audit log archival). Jobs have dependencies—schema refresh must complete before data sync; transformations depend on extraction completing. The system must schedule jobs respecting dependencies (DAG execution), handle failures with retries, and provide visibility into job history for customer support and SLA compliance.

Problem Statement:
Design a batch job processing system that executes jobs on a schedule (cron-like), supports parallel execution, handles job dependencies (DAG), and provides failure handling with retry capabilities. Jobs should be tracked for progress and provide visibility into execution history.

Requirements:

Components to Design:

JobScheduler: Triggers jobs based on schedule (cron expressions)

DependencyResolver: Manages job dependencies (DAG)

ExecutionEngine: Runs jobs in parallel (thread pool)

RetryManager: Handles failed jobs with retry policy

StatusTracker: Tracks job status and execution history

Job Types:

Scheduled jobs: Run on cron schedule (daily, hourly, custom)

Dependent jobs: Run after prerequisite jobs complete

Manual jobs: Triggered on-demand

Recurring jobs: Run repeatedly with interval

Example Scenario:



Daily ETL Job Dependencies:
Job A: Extract from Database (runs at 2:00 AM)
Job B: Transform data (depends on Job A)
Job C: Validate data (depends on Job B)
Job D: Load to warehouse (depends on Job C)
Job E: Generate reports (depends on Job D)
Execution flow:
2:00 AM: Job A starts
2:15 AM: Job A completes → Job B starts
2:30 AM: Job B completes → Job C starts
2:31 AM: Job C fails (validation error)
→ Retry Job C (attempt 2)
2:32 AM: Job C succeeds → Job D starts
2:45 AM: Job D completes → Job E starts
3:00 AM: Job E completes → All jobs done
Status tracking:
Job A: SUCCESS (15 min)
Job B: SUCCESS (15 min)
Job C: SUCCESS after retry (2 min, 1 retry)
Job D: SUCCESS (15 min)
Job E: SUCCESS (15 min)
Total: 62 min (including retry)
What to Look For:

Design Patterns:

Scheduler pattern (cron expression parsing)

DAG-based dependency resolution

Thread pool executor for parallelism

Retry with exponential backoff

State machine for job lifecycle

Scheduling:

Cron expression parsing and evaluation

Timezone handling

Skipped execution handling (catch-up vs skip)

Max concurrent jobs limit

Priority-based scheduling

Dependency Management:

DAG construction and validation (detect cycles)

Topological sort for execution order

Handling failed dependencies (abort downstream vs skip)

Parallel execution of independent jobs

Dynamic dependency resolution

Failure Handling:

Retry policy (max retries, backoff strategy)

Failure notification (email, webhook, Slack)

Error classification (retryable vs non-retryable)

Partial failure handling (some jobs succeed, some fail)

Dead letter queue for permanently failed jobs

State Tracking:

Job status (PENDING, RUNNING, SUCCESS, FAILED, RETRYING)

Execution history (start time, end time, duration)

Error logs and stack traces

Retry attempts tracking

Progress percentage (for long-running jobs)

Performance Optimization:

Thread pool sizing (CPU-bound vs I/O-bound jobs)

Job priority and queue management

Throttling (rate limiting for resource-intensive jobs)

Batch job execution (group similar jobs)

Monitoring:

Jobs pending vs running vs completed

Average execution time per job

Success rate and failure rate

Retry count distribution

SLA tracking (jobs completing on time)

>>>>LLD 3.3: Design a Multi-Source Data Deduplication Engine <<<<<
Category: Distributed Algorithms + State Management

Real-World Context (Hevo Platform):
Hevo customers often have duplicate data across sources (same user in Salesforce, HubSpot, and Zendesk). The deduplication engine identifies duplicates using composite keys (email + phone) or fuzzy matching (handle typos), merges records, and writes a single consolidated record to the destination. With millions of records per day across distributed workers, the dedup store must be partitioned (by hash key), support TTL-based eviction, and handle race conditions when multiple workers process the same user simultaneously.

Problem Statement:
Design a deduplication engine that works across multiple data sources, handling different identifier types (composite keys, fuzzy matching) and supporting high-throughput processing.

Requirements:

Components to Design:

IdentifierExtractor: Extracts unique identifiers from records

DeduplicationStore: Maintains seen identifiers (distributed)

MatchingEngine: Implements different matching strategies

PartitionManager: Distributes dedup work across nodes

GarbageCollector: Cleans up old dedup state

Deduplication Strategies:

Exact match: Same ID across sources

Composite key: Combination of fields (email + name)

Fuzzy match: Similarity score (Levenshtein distance, phonetic matching)

Time-based: Duplicates within time window

Content-based: Hash of record content

Example Scenario:



Deduplicating user records from 3 CRM systems:
Source A: {id: "123", email: "john@example.com", name: "John Smith"}
Source B: {id: "456", email: "john@example.com", name: "Jon Smith"}  // fuzzy
Source C: {id: "789", email: "john@example.com", name: "John Smith"} // exact
Matching results:
→ A and C: Exact match (same email + name)
→ A and B: Fuzzy match (same email, name similarity 95%)
→ Output: 1 consolidated record (merge A, B, C)
What to Look For:

Scalability:

Partitioning strategy (consistent hashing on identifier)

Bloom filter for fast existence check (before expensive lookup)

Multi-level dedup (local cache → distributed cache → database)

Batch processing for throughput

State Management:

TTL-based eviction (remove old identifiers after N days)

Persistent vs in-memory storage tradeoff

State size estimation (1B records × 36 bytes per ID = 36GB)

Compression strategies (integer encoding for IDs)

Matching Algorithms:

Exact match: O(1) hash lookup

Fuzzy match: O(n) or use approximate matching (LSH - Locality Sensitive Hashing)

Performance vs accuracy tradeoff

False positive/negative rates

Conflict Resolution:

Multiple matches found (which record to keep?)

Merge strategy (take latest, prioritize source, manual review)

Audit trail (track dedup decisions)

Distributed Coordination:

Handling dedup across multiple nodes

Avoiding race conditions (two nodes dedup same record)

Eventual consistency vs strong consistency

Split-brain scenarios

>>>>>>>LLD 3.4: Design a Schema Registry with Versioning<<<<<<
Category: Schema Management + Compatibility

Real-World Context (Hevo Platform):
Hevo ingests data from evolving sources—customers add columns to their databases, change data types, or restructure JSON payloads. The schema registry tracks schema versions, validates compatibility (backward/forward/full), and generates migration scripts for destination tables. Without compatibility checks, breaking schema changes cause pipeline failures. The registry must cache schemas for performance (thousands of lookups per second), replicate across regions for HA, and support rollback when schema changes cause data corruption.

Problem Statement:
Design a centralized schema registry that manages schema versions, enforces compatibility rules, and supports schema evolution across distributed services.

Requirements:

Components to Design:

SchemaStore: Persists schema versions

CompatibilityChecker: Validates schema changes

SchemaResolver: Resolves schema by ID or version

MigrationEngine: Generates migration scripts

CacheLayer: High-performance schema lookup

Compatibility Modes:

BACKWARD: New schema can read old data (add optional fields, remove fields)

FORWARD: Old schema can read new data (only add required fields)

FULL: Both backward and forward compatible

NONE: No compatibility check (breaking changes allowed)

Example Scenario:



User schema evolution:
V1: {id: int, name: string}
V2: {id: int, name: string, email: string}  // add optional field
→ BACKWARD compatible (can read V1 data with V2 schema)
V3: {id: int, name: string, email: string (required)}  // make email required
→ NOT BACKWARD compatible (can't read V1 data with V3 schema)
→ Registry rejects V3 if BACKWARD mode enforced
What to Look For:

Design Patterns:

Repository pattern for schema storage

Visitor pattern for schema traversal/validation

Builder pattern for schema creation

Adapter pattern for different schema formats (Avro, Protobuf, JSON Schema)

Versioning Strategy:

Auto-incrementing version numbers (1, 2, 3...)

Git-like versioning with branches

Immutable schemas (versions never change)

Schema deletion policy (soft delete vs hard delete)

Compatibility Checking:

Field addition: allowed (with default value)

Field removal: depends on mode (allowed in BACKWARD)

Type change: usually breaking (int → string)

Renaming: breaking (need migration mapping)

Algorithm complexity: O(n) where n = number of fields

Caching Strategy:

Cache schemas by ID and version

TTL-based invalidation

Cache warming on startup

Distributed cache consistency (invalidate across all nodes)

Migration Support:

Automatic migration script generation

Dry-run mode (test migration without applying)

Rollback support (revert to previous schema version)

Data backfill strategy for new required fields

High Availability:

Multi-region replication

Read replicas for scale

Write consistency (single master vs multi-master)

Conflict resolution for concurrent schema updates

>>>>LLD 3.5: Design a Data Transformation Pipeline<<<<
Category: Data Processing + Configuration-Based Design

Real-World Context (Hevo Platform):
Hevo allows customers to configure transformations via UI: filter rows (age > 18), rename columns, enrich with external APIs (IP to geo-location), and validate data quality. These transformations are stored as JSON configs and executed at runtime. The transformation pipeline must chain operations efficiently, handle per-record errors (skip invalid records), batch API calls for enrichment (avoid 1 API call per record), and provide granular error reporting (which transformation stage failed, which records). This is Hevo's core value-add over raw data replication.

Problem Statement:
Design a data transformation pipeline that applies a chain of configurable transformations to input data. The pipeline should support common transformation operations, handle errors gracefully, and optimize for performance through batching and parallel processing.

Requirements:

Components to Design:

TransformationChain: Manages sequence of transformations

TransformationRegistry: Registers available transformation types

DataValidator: Validates input/output at each stage

ErrorHandler: Handles transformation failures

PerformanceOptimizer: Batching and parallel execution

Transformation Types:

Filter: Remove records based on condition (e.g., age > 18)

Map: Transform fields (rename, compute new fields)

Validate: Check data quality (required fields, format, ranges)

Enrich: Add data from external source (lookup table, API)

Aggregate: Group and compute aggregations (sum, count, avg)

Example Scenario:



Input: User records from CSV
[
  {id: 1, name: "John", age: 25, country_code: "US"},
  {id: 2, name: "Jane", age: 17, country_code: "UK"},
  {id: 3, name: "Bob", age: 30, country_code: "CA"}
]
Transformation Pipeline:
1. Filter: age >= 18
   → Removes Jane (age 17)
2. Map: Rename and compute fields
   - country_code → country
   - Add field: age_group = (age < 30 ? "young" : "senior")
3. Enrich: Lookup country name
   - US → United States
   - CA → Canada
4. Validate: Check required fields
   - Ensure id, name, age, country, age_group are present
Output:
[
  {id: 1, name: "John", age: 25, country: "United States", age_group: "young"},
  {id: 3, name: "Bob", age: 30, country: "Canada", age_group: "senior"}
]
What to Look For:

Design Patterns:

Chain of Responsibility (transformation chain)

Strategy pattern (different transformation types)

Builder pattern (pipeline configuration)

Template method (common transformation logic)

Configuration:

JSON/YAML-based transformation config

Validation of configuration

Dynamic pipeline creation from config

Reusable transformation templates

Error Handling:

Per-record error handling (skip vs fail)

Per-stage error handling (continue vs abort)

Error logging and reporting

Dead letter queue for failed records

Partial failure handling (some records succeed)

Performance Optimization:

Batching records (process 1000 at a time)

Parallel processing (multiple threads)

Caching for enrichment lookups

Lazy evaluation where possible

Avoiding redundant transformations

Validation:

Input validation (before pipeline)

Output validation (after each stage)

Schema validation (field types, required fields)

Business rule validation (value ranges, constraints)

Monitoring:

Records processed per stage

Transformation success/failure rate

Processing time per stage

Bottleneck identification

Error distribution by type

Extensibility:

Adding custom transformation types

Pluggable validators

Custom enrichment sources

Transformation composition (combine multiple)
